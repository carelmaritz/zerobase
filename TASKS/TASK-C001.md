## Objective

Introduce versioned schema migrations with Alembic so that an existing install can be upgraded in place without losing data, and so every later schema change ships as a reviewed migration.

---

## Background

`main.py` calls `Base.metadata.create_all(engine)` on startup. That creates missing tables but never alters existing ones, so the first column added to any table will break or silently diverge on existing installs. The README warns users not to rely on in-place upgrades until this lands.

Almost every roadmap feature needs a schema change (transfer links, hidden/closed flags, import IDs, targets, schedules, cleared status), so this task blocks TASK-H002 to TASK-H006, TASK-M001, TASK-M002 and TASK-M006.

---

## Technical Requirements

- Alembic added as a runtime dependency; migration scripts packaged inside `src/zerobase/` so they ship in the Docker image (`pip install .` only installs the package).
- A baseline revision that reproduces the current schema exactly.
- A constraint **naming convention** on `Base.metadata` (`ix`, `uq`, `ck`, `fk`, `pk`), set before the baseline is generated. Unnamed constraints are painful to alter later, especially on SQLite.
- `render_as_batch=True` so ALTERs work on SQLite (dev and tests).
- The app upgrades the database to head on startup, replacing `create_all`. Must be safe if two processes start at once (Postgres advisory lock, or document single-instance only).
- No pre-migration installs exist (decision 2026-10-21, see Key Decisions). If the app finds application tables but no `alembic_version`, it refuses to start with a clear message explaining dump/restore, rather than stamping or touching the data.
- The database URL comes from `Settings`, not a hard-coded `alembic.ini` value.

### Success Criteria
- [x] Fresh database: app starts, tables are created via migrations, `alembic_version` is at head.
- [x] Database with app tables but no `alembic_version`: app refuses to start with a clear message, data untouched.
- [x] A test asserts migrations at head match the models (`alembic check` or `compare_metadata`) on SQLite and PostgreSQL in CI.
- [x] A test runs upgrade to head then downgrade to base on an empty database.
- [x] README: in-place upgrade warning removed; "how to add a migration" added to Development; backup-before-upgrade advice added.

### Out of Scope

- Any actual schema change beyond the naming convention (each feature task brings its own migration).
- Changing test fixtures away from `create_all` for speed, unless trivial. Unit tests may keep using `create_all`; the drift test above guards correctness.
- Automatic pre-migration backups.

## Work Completed

### Files Created/Modified
- `src/zerobase/migrate.py` - `upgrade_to_head(engine)`: PostgreSQL advisory lock, refuses pre-migration databases (`UnmigratedDatabaseError`), upgrades to head, returns the revision
- `src/zerobase/migrations/env.py`, `script.py.mako` - Alembic environment (uses the app's connection, or `ZEROBASE_DATABASE_URL` from the CLI; batch mode for SQLite)
- `src/zerobase/migrations/versions/0001_baseline_schema.py` - Baseline: the six existing tables, autogenerated and checked by hand against `models.py`
- `src/zerobase/db.py` - Constraint naming convention on `Base.metadata`
- `src/zerobase/main.py` - Lifespan runs `upgrade_to_head` instead of `create_all` and logs the revision
- `alembic.ini` - Developer CLI config (not used by the app)
- `pyproject.toml` - `alembic>=1.13` dependency; migrations included as package data
- `tests/test_migrations.py` - Drift, idempotence, downgrade/upgrade, refusal of pre-migration databases
- `tests/conftest.py` - Teardown also drops `alembic_version`
- `README.md`, `DEPLOYMENT.md` - Removed "no migrations" warnings; added "Database migrations" developer section

### Key Decisions Made
- 2026-10-21: No existing installs with data (first deployment is still to come), so constraint-naming option (c) chosen: the naming convention applies from the baseline, and pre-migration databases are refused rather than stamped. Decided with the user.
- Migrations run in-process at startup (lifespan), not as a separate entrypoint step, so every way of running the app (Docker, uvicorn, tests) gets the same schema.
- The app builds its Alembic `Config` in code and passes its own connection, so no `alembic.ini` ships in the image and the database URL is never put through configparser (passwords containing `%` would break it).
- Tests now run against the migrated schema rather than `create_all`, so all 41 existing tests exercise the real migrations.
- Revision IDs are short sequential numbers (`0001`), set with `--rev-id`, so the order is obvious from file names.

### Implementation Summary
`upgrade_to_head` opens one transaction, takes a PostgreSQL advisory lock (no-op on SQLite), checks for a pre-migration database, then runs `alembic upgrade head` on that connection. The startup log shows `Database schema at revision 0001`.

## Known Issues & Gotchas

- [x] Constraint names: databases created by `create_all` would have database-default names (e.g. `accounts_user_id_fkey`) that differ from the convention. Resolved: no such installs exist; option (c) chosen (see Key Decisions).
- [ ] SQLite cannot ALTER most things; batch mode recreates tables. Fine for tests and dev, but keep migrations simple.
- [ ] `func.extract` and boolean handling already differ between SQLite and Postgres; run the drift test on both.

2. Deploy the previous image

**Validation**:
- App starts and budget figures match those before the upgrade
